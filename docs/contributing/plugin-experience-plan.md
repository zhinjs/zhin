# 插件开发与安装体验改进

常见插件应该围绕业务编写代码。解析、资源绑定、会话寻址、清理和诊断仍由框架负责；便捷接口委托现有 Runtime、Feature、Host、Permission 与统一消息链路。

本计划分阶段验收，未完成项不代表现有 API 已支持。新增公开接口还需要通过真实调用方与类型测试确定，不以示意代码作为正式契约。

进度与交付记录见 [Issue #702](https://github.com/zhinjs/zhin/issues/702)。

## 第一阶段：确定问题修复

| 场景 | 改进 | 验收 |
| --- | --- | --- |
| 编写第一插件 | 教程与 README 使用当前命名目录、稳定版本范围和实例配置；子插件显式声明 Feature 并安装自身依赖 | 从中英文教程提取示例，通过真实 Runtime 发现并派发 ping-pong；插件独立作为应用时明确安装适配器 |
| RSS 订阅 | 按公开消息字段提取会话与发送者，查询包含端点 | 同一平台的两个 Bot 在同一群内互不查询或删除对方订阅；无消息来源明确拒绝 |
| 后台业务发送 | 发送失败或未确认投递不再转成空 ID | 失败、拦截、不支持与投递未知均可识别；状态提示仍由自身处理容错 |
| Console 本地配置 | 按 Runtime 包解析读取 Schema | 根插件、本地包、npm 包、多实例和嵌套 owner 正确定位；缺失与非法 Schema 不混淆 |

本阶段不实现 RSS 自动重试、历史错误目标迁移或投递 outbox。测试不能将合成端点通过解释为真实平台验收。

## 第二阶段：高频创作接口

1. 命令：目录定义静态层级；参数、选项、默认值、约束与帮助集中声明，并推导执行参数类型。错误反馈区别未匹配、校验失败与权限拒绝，不对普通聊天滥报错。
2. 上下文：IM 门面按入站/出站提供默认类型。无消息的 Host 调用继续明确表达缺少消息与交互，不能靠断言伪造。
3. 投递目标：从公开消息模型建立可持久化目标；发送时由当前 Runtime 解析。端点、父频道和线程完整保留，失效时明确拒绝，不改投其他 Bot。
4. 状态：按 owner、用户、会话保存小对象，支持 TTL、事务或原子更新；缺持久服务时明确说明，不静默伪装为持久保存。
5. 配置：统一生成 JSON Schema、TS 类型、默认值与表单元信息；密钥用环境引用，变更生效方式可见。
6. 准入：场景、角色、用户限制委托现有权限机制；冷却与并发控制采用共同机制；审批仍是独立执行关口。

每个接口至少用两类真实插件验收，防止只给单一业务包装函数。验证多人并发、两个插件实例、配置失败和热重载，不增加全局最新值单例。

## 第三阶段：实用插件与安装闭环

优先完成提醒/订阅、关键词回复、群欢迎与管理、查询/状态卡片。一次性提醒与周期任务明确时区、取消、重启恢复、错过执行与重叠策略；业务发送不盲目重试未知投递。

CLI 和 Console 使用同一安装与配置服务：安装 → 依赖检查 → 最小配置 → 适用范围 → 应用/重启 → 当前 generation 就绪 → 功能验证。用户能区别已安装、已声明、缺配置、待重启、已启用和降级；验证需要针对实际插件功能，不能以启动成功代替后台任务验证。

渲染预览显示图片/原生内容/文本与降级原因；长期交互使用独立动作记录，不能保留旧 generation 的闭包。公开测试夹具通过真实发现、解析、权限与消息链路驱动合成端点，实机验收单独记录。

首阶段仅涉及 Console Host 的 Schema 读取。独立 Console 前端的完整安装配置流程、嵌套配置表单与功能验证将在后续阶段验收。
