# 消息没有回复，先看哪一步

先在 Console 打开实际账号和会话，从消息旁的诊断入口或会话顶部“最近诊断”读取记录。诊断只读，不会重新执行消息。读取需要当前 Host 的 full scope Token；没有记录时，先检查是否选对账号、父容器和话题，再确认 Runtime 是否已重启或记录已过期。

“入站处理已结束”只说明这一段链路结束。Agent 后续工作、定时任务和平台受理结果需要分别查看。记录超过上限时会标为不完整，不能从缺少某一步推断它没有发生。

| 看到了什么 | 接下来检查 |
| --- | --- |
| 前缀不匹配 | [确认实际账号的前缀](#command-prefix) |
| 参数或格式无效 | [按帮助修正输入](#command-input) |
| 权限未通过 | [核对规则与真实身份](#permission-denied) |
| 中间件或处理器失败 | [定位对应插件](#plugin-errors) |
| 已交给 Agent、仍在处理 | [查看后续运行](#agent-running) |
| 发送失败或不支持 | [检查目标与消息能力](#delivery-failed) |
| 投递结果不确定 | [先核实，避免重复发送](#delivery-unknown) |
| 图片变成文字、样式降级 | [区分目标能力和渲染资源](#message-rendering) |

## 前缀不匹配 {#command-prefix}

前缀属于实际接收消息的账号。同一个 Bot 项目中的两个账号可以有不同前缀，不要根据另一个账号的用法判断当前消息。

检查 Endpoint 的配置与当前生效版本。没有自定义菜单关键词时，可发送 `菜单`；只有当前账号要求 `/` 时才发送 `/菜单`。未匹配前缀的消息仍可能进入普通聊天链，并非一定是错误。

修正后用一条无副作用命令验证，诊断应显示命令命中。菜单分页与自定义关键词见[命令菜单](../authoring/commands.md#查看已加载的指令菜单)。

## 参数或格式无效 {#command-input}

查看命令返回的帮助，或发送该命令的 `--help`，例如 `remind --help`，并使用当前账号的前缀与插件命名空间。帮助读取仍受命令权限约束。

核对参数顺序、必填项、引号以及选项值。`invalid` 表示没有进入该次命令的业务执行；修正后应看到 `executed`，再检查它是否产生实际投递。详见[参数、选项与帮助](../authoring/commands.md)。

## 权限未通过 {#permission-denied}

先确认命令声明和发送者在这个会话中的真实身份。`group(id)` 等规则只匹配类型和 ID，不能据此推断已限制到某个 Bot、父频道或话题。`master` 只隐含 `trusted`，不会自动成为平台管理员。

若 Console 提供权限说明，可先查看声明；手工填写的角色只是模拟。平台或自定义 checker 未执行时应显示“未评估”，不要因为模拟条件匹配就放开实际权限。修改后以有权限和无权限的身份分别验证，拒绝请求不应执行业务。详见[权限](../authoring/commands.md#权限)。

## 中间件或消息处理器失败 {#plugin-errors}

用记录的时间、运行代和插件实例对照 Host 日志。中间件“已进入”但未结束，也可能是下游抛错；只有明确的失败步骤才可归因于该阶段。出站审核或改写失败时，检查对应出站插件，而不是重发同一条业务操作。

修复后先在测试环境复现原场景，再确认处理链与投递记录。诊断不保存正文和原始异常；排查材料也不需要携带密钥。插件执行顺序见[消息流](../concepts/message-flow.md)。

## 已交给 Agent 或仍在处理 {#agent-running}

“已交给 Agent”是交接事实，后续可能等待模型、工具或人工审批。打开同一会话的 Agent 运行记录查看实际阶段。入站诊断没有关联投递，不代表 Agent 已失败或已完成。

只有实际运行支持取消时才执行取消；不要连续发送相同请求试图推进它。工具审批与策略问题见[工具等待审批或被策略拒绝](./index.md#tool-approval-stuck)。

## 发送失败或平台不支持 {#delivery-failed}

先看每条投递记录的实际目标和结果码。确认目标账号在线、会话身份正确，并核对该 Endpoint 声明支持的消息类型。账号能发送文字，不代表支持图片、Markdown 或按钮；平台受理也不保证接收者已读。

在明确确认原请求未发送后，先用测试目标验证最小文字消息。若结果不确定，按下一节处理。Endpoint 离线时见[连接排查](./index.md#endpoint-offline)。

## 投递结果不确定 {#delivery-unknown}

先到原目标会话查看实际结果，再读取对应任务或操作回执核对。网络断开、进程中断或缺少可信回执都可能发生在平台已经处理请求之后。

不要把 `unknown` 当作明确失败自动重试，也不要重新创建同一任务来“补发”。管理员任务应先做只读对账；可用动作以任务提供方实际返回为准。个人提醒的核对步骤见[提醒指南](../solutions/reminders.md)。

## 图片或样式降级为文字 {#message-rendering}

分开检查两件事：当前目标是否支持图片，以及 Runtime 是否有可用的 HTML 渲染器。两者都满足时才可能生成并发送图片。Markdown、图片、按钮也是独立能力，不由其中一种推断另一种。

查看投递记录中的渲染路径和降级事实。缺少资源、渲染失败或目标不支持时，可读文字应保留链接、列表与必要操作信息。文字可读且已受理，说明降级路径可用；若出现原始 HTML 或内部对象，再检查渲染和适配器声明。详见[跨平台渲染](../concepts/message-flow.md)。
